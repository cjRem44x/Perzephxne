# Status & Next Work

Perzephxne is in beta. The book is intended to be the complete language reference for the current compiler and shipped standard library.

The reference currently covers:

- source layout, project manifests, and `przp` commands
- literals, variables, primitive types, arrays, slices, strings, tuples, and failable types
- functions, first-class function pointers, extern declarations, inline functions, and return inference
- control flow, `when`, loops, labels, `break`, `continue`, `goto`, and `defer`
- structs, `impl` methods, generic functions, generic structs, enums, plain unions, and tagged unions
- inline `mod` namespaces and `=>` as a module-access operator interchangeable with `.`
- raw pointers, heap allocation, smart pointers, globals, platform constants, inline assembly, builtins, operators, and naming conventions
- all standard library modules shipped under `compiler/std`

## Product Gaps

The core language surface is represented in the book and regression suite. The remaining work is mostly product hardening:

| Area | Next Work |
|---|---|
| Parser diagnostics | Add focused malformed-syntax regressions and improve messages for missing braces, bad signatures, and invalid generic declarations. |
| Diagnostic consistency | Continue moving command, manifest, import, semantic, and codegen failures toward source-located errors where possible. |
| Regression breadth | Add more edge-case tests for parser recovery, generic instantiation, failable destructuring, and unsafe pointer operations. |
| Build/runtime portability | Keep Linux x86-64 as the current target, then audit assumptions before broadening platform support. |
| Package dependencies | `przp add <name>[@ref]` fetches `github.com/cjRem44x/przp_dep_<name>`, pins the exact resolved commit in `przp.lock`, and `przp build`/`run`/`test` auto-fetch a missing/stale checkout from that pin — see [Build System](./build-system.md#dependencies). Deliberately MVP-scoped: exact-ref pinning only (no semver ranges/version resolution), no global cache (each project gets its own `.przp/deps/`), no auth (public repos only), no `przp update` yet (re-run `przp add <name>` to move to a newer commit on the same ref). `[build].link` remains separate — it covers linking against system libraries the OS already ships (e.g. `link = ["X11", "GL"]`), not a package resolver. |
| Release UX | A future version command should be `przp version`, but versioning is intentionally deferred while beta work is moving quickly. |
| `any` type | Reserved keyword. Runtime-tagged values (boxing, type IDs, `when` dispatch on types) are designed but not implemented; removed from the reference until they exist. |
| Generic return-type substitution through a compound type-application, still open | A generic function's return-type annotation that wraps the type parameter in another generic type application — e.g. `fn wrap<T>(x: T) -> Box<*T>` — does not substitute correctly even after the `gen_type_str`/`type_to_str` fix above: `subst_mangled`'s substitution is a string search for the type parameter's name delimited by `__` (e.g. `"__T"`) inside the already-flattened mangled name, but `type_to_str`'s own pointer/slice/array cases join with a single underscore (`Box<*T>` mangles to `"Box__ptr_T"`, where the delimiter immediately before the bare `T` is `_ptr_` not `__`), so the search never matches and the substitution silently no-ops. The deeper issue is architectural: the parser flattens a generic type application into one opaque mangled string at parse time, discarding the structure sema would need to substitute into it correctly; a real fix means preserving that structure through to substitution time rather than patching the string-matching. Confirmed via `wrap<i32>(5)` giving `error: cannot initialize 'Box__ptr_i32' with value of type 'Box__ptr_T'`. Deferred rather than fixed in the generic-inference change above, which was scoped to call-site inference only. |
| Function calls returning a struct/array by value can't have fields or elements chained directly, still open | Every aggregate-typed expression (`EXPR_IDENT`, `EXPR_FIELD`, `EXPR_INDEX`, `EXPR_STRUCT_LIT`, `EXPR_SMARTDEREF`) is represented in codegen as a *pointer* to the aggregate so chained access (`.field`, `[i]`) can GEP directly — but a plain function call returning a struct/array by value (`EXPR_CALL`) never joined that convention, so `make_point(1, 1).x` fails to compile with a raw LLVM type mismatch ("defined with type '%Point' but expected 'ptr'"). Confirmed with a minimal, generics-unrelated repro. A fix was attempted (spilling the call's by-value result into a fresh alloca and returning its pointer, mirroring every other aggregate-typed expression) but reverted after it broke 8 existing tests (`field_aggregate_ptr_convention`, `struct_abi`, `struct_abi_no_import`, `std_audio`, `std_audio_control`, `std_sync`, `diamond_import`, `array_size_across_import`) — every existing `EXPR_CALL` consumer across codegen currently assumes a *value*, not a pointer, for an aggregate-typed call result, so fixing this needs the same kind of full-consumer audit the `EXPR_FIELD` allowlist bug above got, not a local change at the call site. |
| astro_blaster reported stutter, still open | A stutter reported during rapid fire in `examples/games/astro_blaster` survived three rounds of fixes to `std/audio` (non-blocking writes, an `snd_pcm_avail_update` pre-check, then a full background-thread rewrite) and reproduces with audio skipped entirely (`przp run --no-audio`) — so it isn't audio. `std/gdev`'s own frame timer (`get_frame_time`, real wall-clock via `os.monotonic_ms`) never recorded a frame over 33ms during a session where the stutter was reported, which is the actually strange part: whatever's happening either isn't visible on that clock at all (input-latency-shaped, not render-loop-shaped) or is smaller than the 33ms threshold currently logged. The diagnostic (`[STALL]` logging in `main.przp`) is still in place for whoever picks this back up. |

## Bugs Found and Fixed Along the Way

- **Nested-import local-variable collision** — a 3+-level-deep import chain (file A imports B, B imports C) could mis-rewrite an unrelated local variable inside C's own function body if its name happened to match a top-level item name declared in B. `mangle_items` merges an already-mangled imported module's items into the importer's own item list *before* the importer's own alias-rewrite pass runs, so that pass's name-match set ended up including names with no relation to the code it was walking, and the rewrite itself had no notion of lexical scope to tell a local apart from an item reference. Fixed by collecting each function's own locals (`LocalNames` in `main.c`) and always letting a local name shadow an outer item for that whole function body. Covered by `tests/run/local_name_collision.przp`.
- **Diamond imports produced two incompatible types for the same struct** — a file that imported some module both directly *and* transitively (through a second module that itself imports it) got two different mangled names for the same underlying type, depending on which path reached it — e.g. `sh__Point` via the direct import, `wr__sh__Point` via the transitive one — because `mangle_items` named a module's items by the alias chain used to reach it rather than the module's own identity, and nested imports always picked up one *extra* prefix layer every time the module holding them was itself re-imported. This blocked exactly the layering `std/gdev` needs (a program importing both `std/gdev` and `std/graphics` directly, passing `Rectangle`/`Vector2`/`Texture` values between them). Fixed by freezing an item's name (`Item.mangled` in `ast.h`) the moment it's merged in via a cross-file `import()` — no later `mangle_items` pass may prefix it again — and letting the existing merged-import cache (previously top-level-imports-only) apply at any nesting depth, so a second import of the same (path, alias) pair anywhere in the compile reuses the first one's already-frozen names instead of re-parsing a differently-prefixed copy. Deliberately scoped to cross-file imports only — a same-file `mod Name {}` block's own items (`expand_mod_items`) still pick up the containing file's import alias when that file is imported elsewhere, unaffected by this change (see `tests/run/mod_in_imported_file.przp`). Covered by `tests/run/diamond_import.przp`.

- **A statement starting with `(` or `[` could be silently swallowed as a call/index continuation of the previous statement** — the grammar has no semicolons and relies entirely on each statement's own expression parsing stopping at the right point; `parse_postfix`'s call (`(`) and index (`[`) continuations had no check for a newline in between, so `a: i32 = foo()` followed by `(a + 1)` on the next line parsed as one statement, `a: i32 = foo()(a + 1)` — calling `foo()`'s result with `(a + 1)` as an argument, silently absorbing what was meant to be an independent next statement. This surfaced first as a parse error ("unexpected token '=' in expression") for a deref-assignment (`(dst + x).* = value`) written directly in a function's own top-level body, but the underlying issue is general and would have silently miscompiled (not errored) any case where the "merged" interpretation happened to still type-check. Fixed by tracking each token's source line (`Parser.prev_end_line`) and only treating `(`/`[` as a continuation when it starts on the same line the previous token ended on. Covered by `tests/run/postfix_newline_boundary.przp`.
- **`@alo(T, N)`/`@realo(ptr, T, N)` silently ignored `N` whenever it wasn't a literal integer** — codegen's count-argument handling only recognized a literal (`EXPR_INT`) and fell back to allocating/resizing for exactly 1 element for anything else (a variable, a computed expression), a heap buffer overflow on every write past the first element with no error at compile or run time. Found while writing `std/image`'s GIF decoder: a growable array of frame structs sized by a variable (`frames_cap`) corrupted an unrelated, already-populated slot a few writes later. Fixed by evaluating the count argument as a real expression, mirroring how `@realo`'s count argument already worked correctly when explicitly passed — which also exposed an identical, separate, latent bug in `@realo`'s own no-count-argument fallback path (invalid LLVM IR, a constant-expression form used directly as an instruction), fixed the same way. Covered by `tests/run/alo_variable_count.przp`.
- **A negative literal in a global's initializer failed to compile** — `X: i32 = -12` reported "global initializer must be a compile-time constant", even though it plainly is one. `-12` parses as `UNOP_NEG` over a positive `EXPR_INT`, not a single literal node, and the constant emitter that walks a global's initializer expression only recognized bare literals, struct/array literals, and function references — a unary negation of one of those wasn't among them. Found writing `std/audio`'s libmpg123 status-code constants (`MPG123_DONE = -12`, `MPG123_NEW_FORMAT = -11`), which are negative by definition. Fixed by folding one level of `UNOP_NEG` over an `EXPR_INT`/`EXPR_FLOAT` operand into the equivalent negative constant. Covered by `tests/run/global_negative_const.przp`.
- **An `f32` (or `f16`) global initialized with a literal not exactly representable at that width failed to compile** — `X: f32 = 3.6` reported "floating point constant invalid for type". LLVM IR's hex-float constant syntax requires the encoded bit pattern to be exactly representable at the constant's declared type; the global-initializer constant emitter always encoded a float literal using its raw `f64` bit pattern regardless of the declared type, while the equivalent non-global expression path (`cg_expr`) already rounded through the target type first for exactly this reason. Found writing `examples/games/astro_blaster`'s `SHIP_ROT_SPEED: f32 = 3.6`. Fixed by applying the same `f32`/`f16` rounding to the global-initializer path (and to this same session's `UNOP_NEG` literal-folding above, which had the identical gap). Covered by `tests/run/global_f32_const.przp`.
- **`obj.field = <struct or array literal>` stored the literal's pointer instead of its bytes, when `field` is itself a struct/array** — every other lvalue shape that can receive a struct/array literal RHS (`p.* =`, `p.^ =`, `arr[i] =`) already loads the aggregate through its returned alloca pointer before storing it (see the earlier "`p.* = <struct or array literal>`" entry), but the plain `x.field = ...` shape was missed, so it stored the pointer value itself where a `%Struct` value was expected — a hard type-mismatch at the LLVM IR level rather than a silent miscompile, since the two never happen to have the same bit width. Found writing `examples/games/astro_blaster`'s `asteroids[i].pos = gfx.Vector2{...}`. Fixed by adding the same load-before-store guard to this lvalue shape. Covered by `tests/run/field_assign_struct_lit.przp`.
- **Float-width coercion (`f64` ↔ `f32`) was missing from every scalar-store path except `let`'s** — assigning an `f64`-typed value (most commonly a bare literal that defaults to `f64`, e.g. `dt = 1.0 / 60.0` or a struct-literal field `Ship{.angle=-1.5707963}`) into an `f32`-typed target failed to compile with a raw LLVM type-mismatch, because the integer-width (`trunc`/`sext`/`zext`) coercion these scalar-store sites already had was never given a matching `fptrunc`/`fpext` case — except `STMT_LET`'s own scalar store, which had had it from the start. Found writing `examples/games/astro_blaster` (a struct-literal field assignment and a plain identifier reassignment, both real, unremarkable lines of game code). Fixed by adding the same float-width case struct-literal field-store and both plain/compound identifier-assignment paths already had a template for in `STMT_LET`. Covered by `tests/run/float_width_coerce.przp`.
- **`EXPR_FIELD` (a struct/array-typed field access, e.g. `holder.point`) was missing from every "does this expression return a pointer to the aggregate" allowlist across codegen** — `EXPR_FIELD`'s own `cg_expr` case returns the field's pointer (not a loaded value) for aggregate field types, explicitly "so chained access works," the same convention `EXPR_IDENT`/`EXPR_STRUCT_LIT`/`EXPR_INDEX`/`EXPR_SMARTDEREF` already follow — but every site built to recognize that convention (`STMT_LET`'s scalar init, `@ok`/`@new`'s argument handling, three `STMT_ASSIGN` target shapes' RHS handling, and `STMT_RET`) had an allowlist of expression kinds that simply never included it (and a couple were separately missing `EXPR_INDEX` too). Found writing `examples/games/astro_blaster`'s asteroid-splitting mechanic: `hit_pos: gfx.Vector2 = asteroids[ai].pos` failed to compile with the same class of raw LLVM type-mismatch as the earlier, narrower `obj.field = <literal>` bug above. Fixed by adding `EXPR_FIELD` (and `EXPR_INDEX` where absent) to all eight sites in one sweep rather than re-discovering each one individually. Covered by `tests/run/field_aggregate_ptr_convention.przp`.
- **Generic function calls could not infer their type arguments from actual argument types, contradicting the book's own documented example** — `book/src/generics.md` has always shown `y: f64 = max(1.5, 0.7)  # inferred from args` right alongside the explicit `max<i32>(10, 20)` form, but only the explicit form ever worked; `biggest(1.5, 0.7)` failed with "undefined identifier 'biggest'". Root cause: instantiation was driven entirely by `GenInst` entries the parser records only when it sees literal `name<Type>(...)` syntax, while `sema.c`'s `lookup()` is a pure scope-chain walk that never consults the uninstantiated-template list (`s->generics`) on a miss — the two structures never cross-referenced each other, so a bare `name(args)` call against a generic template had no path to ever resolve. Fixed by adding inference directly in `EXPR_CALL`: when a bare-identifier callee doesn't resolve via `lookup()`, search `s->generics` for a matching template, type-check the arguments early, and recursively unify each parameter's declared type against its argument's actual type (`unify_generic_type`, the mirror image of the existing `subst_type`) to bind concrete types per type-parameter, erroring clearly on a binding conflict (two arguments implying different concrete types for the same parameter) or an unbound parameter (one that appears only in the return type, with nothing to infer it from). A matched, fully-bound call is mangled with the same scheme the parser's explicit-syntax path already uses (`type_to_str`, unstaticked from `parser.c` for reuse) and instantiated-or-reused exactly as an explicit call would be, so repeated inferred calls at the same concrete type share one instantiation. Along the way, two more real, independent bugs surfaced and were fixed in the same change: `sema.c`'s own `gen_type_str` (used to build mangled names for template substitution) was missing cases for pointer/smart-pointer/slice/array types entirely, silently falling back to the literal, wrong type-parameter name (confirmed with `fn wrap<T>(x: T) -> Box<*T>`) — deleted in favor of reusing the same now-shared `type_to_str`; and `subst_type` had no case at all for `TY_TUPLE`, so a generic function returning a tuple (`fn pair<A, B>(a: A, b: B) -> (A, B)`) never got its element types substituted, leaving the return type as the literal, unresolved `(A, B)` regardless of what `A`/`B` were bound to. Covered by `tests/run/generic_infer_basic.przp`, `tests/run/generic_infer_multi_param.przp` (exercises the `TY_TUPLE` fix), `tests/run/generic_infer_wrapped.przp` (exercises the recursive unify case through a slice), `tests/fail/generic_infer_conflict.przp`, and `tests/fail/generic_infer_unbound.przp`.
- **A struct field or index expression passed as a non-`self` argument to a method call was passed as a raw, unloaded pointer instead of the aggregate's value** — `other.add(ship.vel)` (a `Vector2.add` call, `ship.vel` a struct field) failed to compile with a raw LLVM type mismatch (`ptr` where the struct's value type was expected). Codegen's method-call argument-lowering had an allowlist of expression kinds that "need loading from the pointer convention" (`EXPR_IDENT`, `EXPR_STRUCT_LIT`) — the same shape as the earlier `EXPR_FIELD`-missing-from-every-allowlist bug in this list, just a ninth site that sweep didn't cover, since that one was scoped to `STMT_LET`/`@ok`/`@new`/`STMT_ASSIGN`/`STMT_RET`, not a method call's own argument lowering. Found writing `Vector2` arithmetic (`add`/`sub`/`scale`/`dot`) for `std/graphics` in support of `std/gdev`'s new frame-rate-independent helpers. Fixed by matching the plain-function-call argument path a few lines below in `codegen.c`, which already used the more robust "load everything except `EXPR_CALL`" exclusion instead of allowlisting specific pointer-returning kinds — the same fix shape, applied to the one path that had drifted from it. Covered by `tests/gl/method_call_field_arg`.
- **A struct's own array-size constant broke the moment the module declaring it was imported by anything** — `[CAP]T` (a named `::` constant as an array size) folds correctly when a file is compiled standalone (`array_size_const.przp`), but once that same file is `import()`-ed, `mangle_items` prefixes the constant's own item name to `alias__CAP` (so sema's pass-1.7 pre-registration and `eval_const_int`'s later lookup both key off the mangled name) while the `EXPR_IDENT` sitting inside the struct's own `TY_ARRAY.size` kept referencing the pre-mangling name `CAP` — `rw_type`'s `TY_ARRAY` case rewrote the array's *element* type (`array.inner`) but never walked `array.size` at all, unlike the identical shape inside a function body or a global's own initializer, both of which `rw_ident_stmts`/`rw_ident_expr` already covered elsewhere in `mangle_items`. Found (then worked around with a literal, then properly fixed) writing `std/audio`'s `AudioCtrl.queue: [AUDIO_QUEUE_CAP]AudioRequest`. Fixed by calling `rw_ident_expr` on `array.size` from `rw_type`'s `TY_ARRAY` case, same as any other module-local identifier reference (passing no `LocalNames`, since a type's own array-size expression can't reference a function-local the way a body statement can). Covered by `tests/run/array_size_across_import.przp` (plus its `helpers/array_size_import_helper.przp`), covering both a bare constant and arithmetic on one (`BASE * 2`) through an import boundary.

## Documentation Rule

Any compiler feature that is added or changed should update both the book source and the generated `book/book` output in the same change. The book should remain the user-facing source of truth for the current language.

# Status & Next Work

Perzephxne is in beta. The book is intended to be the complete language reference for the current compiler and shipped standard library.

The reference currently covers:

- source layout, project manifests, and `przp` commands
- literals, variables, primitive types, arrays, slices, strings, tuples, and failable types
- functions, first-class function pointers, extern declarations, inline functions, and return inference
- control flow, `when`, loops, labels, `break`, `continue`, `goto`, and `defer`
- structs, `impl` methods, generic functions, generic structs, enums, plain unions, and tagged unions
- inline `mod` namespaces and `=>` as a module-access operator interchangeable with `.`
- raw pointers, heap allocation, smart pointers, globals, platform constants, inline assembly, builtins, operators, and naming conventions
- all standard library modules shipped under `compiler/std`

## Product Gaps

The core language surface is represented in the book and regression suite. The remaining work is mostly product hardening:

| Area | Next Work |
|---|---|
| Parser diagnostics | Add focused malformed-syntax regressions and improve messages for missing braces, bad signatures, and invalid generic declarations. |
| Diagnostic consistency | Continue moving command, manifest, import, semantic, and codegen failures toward source-located errors where possible. |
| Regression breadth | Add more edge-case tests for parser recovery, generic instantiation, failable destructuring, and unsafe pointer operations. |
| Build/runtime portability | Keep Linux x86-64 as the current target, then audit assumptions before broadening platform support. |
| Package dependencies | `[deps]` is reserved. There is no external resolver yet; Core/Stdlib ships with the language. `[build].link` (see [Build System](./build-system.md)) covers linking against system libraries the OS already ships (e.g. `link = ["X11", "GL"]`) — this is not a package resolver, just linker flags. |
| Release UX | A future version command should be `przp version`, but versioning is intentionally deferred while beta work is moving quickly. |
| `any` type | Reserved keyword. Runtime-tagged values (boxing, type IDs, `when` dispatch on types) are designed but not implemented; removed from the reference until they exist. |

## Bugs Found and Fixed Along the Way

- **Nested-import local-variable collision** — a 3+-level-deep import chain (file A imports B, B imports C) could mis-rewrite an unrelated local variable inside C's own function body if its name happened to match a top-level item name declared in B. `mangle_items` merges an already-mangled imported module's items into the importer's own item list *before* the importer's own alias-rewrite pass runs, so that pass's name-match set ended up including names with no relation to the code it was walking, and the rewrite itself had no notion of lexical scope to tell a local apart from an item reference. Fixed by collecting each function's own locals (`LocalNames` in `main.c`) and always letting a local name shadow an outer item for that whole function body. Covered by `tests/run/local_name_collision.przp`.
- **Diamond imports produced two incompatible types for the same struct** — a file that imported some module both directly *and* transitively (through a second module that itself imports it) got two different mangled names for the same underlying type, depending on which path reached it — e.g. `sh__Point` via the direct import, `wr__sh__Point` via the transitive one — because `mangle_items` named a module's items by the alias chain used to reach it rather than the module's own identity, and nested imports always picked up one *extra* prefix layer every time the module holding them was itself re-imported. This blocked exactly the layering `std/gdev` needs (a program importing both `std/gdev` and `std/graphics` directly, passing `Rectangle`/`Vector2`/`Texture` values between them). Fixed by freezing an item's name (`Item.mangled` in `ast.h`) the moment it's merged in via a cross-file `import()` — no later `mangle_items` pass may prefix it again — and letting the existing merged-import cache (previously top-level-imports-only) apply at any nesting depth, so a second import of the same (path, alias) pair anywhere in the compile reuses the first one's already-frozen names instead of re-parsing a differently-prefixed copy. Deliberately scoped to cross-file imports only — a same-file `mod Name {}` block's own items (`expand_mod_items`) still pick up the containing file's import alias when that file is imported elsewhere, unaffected by this change (see `tests/run/mod_in_imported_file.przp`). Covered by `tests/run/diamond_import.przp`.

- **A statement starting with `(` or `[` could be silently swallowed as a call/index continuation of the previous statement** — the grammar has no semicolons and relies entirely on each statement's own expression parsing stopping at the right point; `parse_postfix`'s call (`(`) and index (`[`) continuations had no check for a newline in between, so `a: i32 = foo()` followed by `(a + 1)` on the next line parsed as one statement, `a: i32 = foo()(a + 1)` — calling `foo()`'s result with `(a + 1)` as an argument, silently absorbing what was meant to be an independent next statement. This surfaced first as a parse error ("unexpected token '=' in expression") for a deref-assignment (`(dst + x).* = value`) written directly in a function's own top-level body, but the underlying issue is general and would have silently miscompiled (not errored) any case where the "merged" interpretation happened to still type-check. Fixed by tracking each token's source line (`Parser.prev_end_line`) and only treating `(`/`[` as a continuation when it starts on the same line the previous token ended on. Covered by `tests/run/postfix_newline_boundary.przp`.
- **`@alo(T, N)`/`@realo(ptr, T, N)` silently ignored `N` whenever it wasn't a literal integer** — codegen's count-argument handling only recognized a literal (`EXPR_INT`) and fell back to allocating/resizing for exactly 1 element for anything else (a variable, a computed expression), a heap buffer overflow on every write past the first element with no error at compile or run time. Found while writing `std/image`'s GIF decoder: a growable array of frame structs sized by a variable (`frames_cap`) corrupted an unrelated, already-populated slot a few writes later. Fixed by evaluating the count argument as a real expression, mirroring how `@realo`'s count argument already worked correctly when explicitly passed — which also exposed an identical, separate, latent bug in `@realo`'s own no-count-argument fallback path (invalid LLVM IR, a constant-expression form used directly as an instruction), fixed the same way. Covered by `tests/run/alo_variable_count.przp`.
- **A negative literal in a global's initializer failed to compile** — `X: i32 = -12` reported "global initializer must be a compile-time constant", even though it plainly is one. `-12` parses as `UNOP_NEG` over a positive `EXPR_INT`, not a single literal node, and the constant emitter that walks a global's initializer expression only recognized bare literals, struct/array literals, and function references — a unary negation of one of those wasn't among them. Found writing `std/audio`'s libmpg123 status-code constants (`MPG123_DONE = -12`, `MPG123_NEW_FORMAT = -11`), which are negative by definition. Fixed by folding one level of `UNOP_NEG` over an `EXPR_INT`/`EXPR_FLOAT` operand into the equivalent negative constant. Covered by `tests/run/global_negative_const.przp`.
- **An `f32` (or `f16`) global initialized with a literal not exactly representable at that width failed to compile** — `X: f32 = 3.6` reported "floating point constant invalid for type". LLVM IR's hex-float constant syntax requires the encoded bit pattern to be exactly representable at the constant's declared type; the global-initializer constant emitter always encoded a float literal using its raw `f64` bit pattern regardless of the declared type, while the equivalent non-global expression path (`cg_expr`) already rounded through the target type first for exactly this reason. Found writing `examples/games/astro_blaster`'s `SHIP_ROT_SPEED: f32 = 3.6`. Fixed by applying the same `f32`/`f16` rounding to the global-initializer path (and to this same session's `UNOP_NEG` literal-folding above, which had the identical gap). Covered by `tests/run/global_f32_const.przp`.
- **`obj.field = <struct or array literal>` stored the literal's pointer instead of its bytes, when `field` is itself a struct/array** — every other lvalue shape that can receive a struct/array literal RHS (`p.* =`, `p.^ =`, `arr[i] =`) already loads the aggregate through its returned alloca pointer before storing it (see the earlier "`p.* = <struct or array literal>`" entry), but the plain `x.field = ...` shape was missed, so it stored the pointer value itself where a `%Struct` value was expected — a hard type-mismatch at the LLVM IR level rather than a silent miscompile, since the two never happen to have the same bit width. Found writing `examples/games/astro_blaster`'s `asteroids[i].pos = gfx.Vector2{...}`. Fixed by adding the same load-before-store guard to this lvalue shape. Covered by `tests/run/field_assign_struct_lit.przp`.
- **Float-width coercion (`f64` ↔ `f32`) was missing from every scalar-store path except `let`'s** — assigning an `f64`-typed value (most commonly a bare literal that defaults to `f64`, e.g. `dt = 1.0 / 60.0` or a struct-literal field `Ship{.angle=-1.5707963}`) into an `f32`-typed target failed to compile with a raw LLVM type-mismatch, because the integer-width (`trunc`/`sext`/`zext`) coercion these scalar-store sites already had was never given a matching `fptrunc`/`fpext` case — except `STMT_LET`'s own scalar store, which had had it from the start. Found writing `examples/games/astro_blaster` (a struct-literal field assignment and a plain identifier reassignment, both real, unremarkable lines of game code). Fixed by adding the same float-width case struct-literal field-store and both plain/compound identifier-assignment paths already had a template for in `STMT_LET`. Covered by `tests/run/float_width_coerce.przp`.

## Documentation Rule

Any compiler feature that is added or changed should update both the book source and the generated `book/book` output in the same change. The book should remain the user-facing source of truth for the current language.
